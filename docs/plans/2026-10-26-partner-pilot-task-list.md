## 0. הנחות (לתקן אם שגויות — משנה את §B)

- **"שותפים" = משרדי רו"ח / הנה"ח** שמביאים לקוחות עצמאיים. שלושה משטחים: **לקוח** (PWA), **שותף** (פורטל תיק לקוחות), **countme** (ops).
- **"sql injection" בבקשה = Text-to-SQL** (שקל שולף נתונים בשאילתה חופשית). הגנה מפני SQL injection כחולשה היא פריט נפרד (A10).
- הלקוח הוא הבעלים של הנתונים; השותף מקבל גישה **מואצלת, מפורשת וניתנת לביטול**.

## 1. ממצאי מפתח מהריפו (משנים את התוכנית)

1. **אין היום ledger.** מודל הנתונים הוא `profiles.persona` (JSONB); 6 הטבלאות הרלציוניות נמחקו ב-13/08 (`20260813120000_…`), ותוכנית הפיצול (`persona-split-plan`) רק תכנון. **קליטת היסטוריה מקובץ אחיד לא ניתנת ל-JSONB** → ה-ledger הקנוני (B2) הוא **המסלול הקריטי**.
2. **אין שכבת שותף.** יש `/admin` לפי `ADMIN_EMAILS` בלבד; אין ארגון→לקוחות, תפקידים, הסכמה, audit.
3. **אין parser לקובץ אחיד** (אפס אזכורים בקוד). הוא מודול מבודד (פונקציות טהורות + fixtures) — מתאים ל-loop ארוך של coding agent.
4. **PWA קיים** (`manifest.json`, `sw.js`), **אין Push**. התראות היום = דייג'סט מייל (Resend + Cron). מנוע ההתראות (`lib/alerts`, `deadlines`, `ceiling`) קיים ונשתמש בו.
5. **שקל** כבר בנוי כ-tool-use מעל מחשבונים דטרמיניסטיים + RAG חינמי + `client-graph`. הכיוון הנכון: להרחיב כלים מעל ה-ledger; Text-to-SQL רק לזנב הארוך ובשכבה מוגבלת (E2).
6. **חשבונית ישראל:** המחקר מ-20/08 מצא שאין "תור אישורי ספק" — זו אינטגרציית API עצמאית. מה שחסום הוא **רישום + credentials**. בונים מעל interface עם sandbox/mock; "קוד זמני" = env, בלי שינוי קוד במעבר (G1).
7. **תשלומים:** מושעים (נעול 03/08), `BILLING_ENABLED` כבוי. המלצה: לא לבנות IAP לפיילוט (H7).
