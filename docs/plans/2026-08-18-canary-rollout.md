# Canary Rollout — פיצ'ר-פלאגים הדרגתיים (v2 plan item 5.3)

**רקע:** ל-Vercel Hobby (התוכנית שאנחנו עליה) אין canary deployment מובנה —
אי אפשר לשלוח 10% מהתנועה לגרסה חדשה ברמת ה-hosting. התחליף הריאלי: feature
flag בקוד, עם אחוז-חשיפה מוגדר ב-env, שמכניס משתמשים לפיצ'ר החדש בהדרגה לפי
hash דטרמיניסטי של ה-user id. המימוש: `src/lib/rollout.ts` (טסטים:
`tests/unit/rollout.test.ts`).

## מתי לעטוף פיצ'ר ב-rollout flag

לא כל שינוי צריך flag — זה תקורה (קוד + החלטה-מתי-להסיר). לעטוף כש:

- **מסוכן** — נוגע בחישוב מס/כסף אמיתי, בזרימת נתונים קריטית (persona,
  chat history), או במשהו שקשה לשחזר אם משתמש נתקל בבאג (למשל: מנוע תמחור
  חדש, לוגיקת ניקוד-זיכוי חדשה).
- **יקר** — קורא ל-AI API בנפח גדול, מוסיף קריאות DB כבדות, או משנה משהו
  שמשפיע על עלות (budget guard, caps).
- **ניסיוני** — אנחנו לא בטוחים שהעיצוב/UX נכון ורוצים למדוד לפני שכולם
  רואים (onboarding חדש, שינוי ניווט גדול).

פיצ'ר קטן, הפיך בקלות (סגנון, טקסט, תיקון-באג נקודתי) — **לא** צריך flag,
פשוט לדחוף.

## שימוש בקוד

```ts
import { inRollout } from "@/lib/rollout";

// צד שרת (API route / server component) — בלי rebuild כשמשנים את ה-env:
if (inRollout("new-pricing-engine", user?.id)) {
  return newPricingEngine(input);
}
return legacyPricingEngine(input);

// צד לקוח (UI gating) — קורא NEXT_PUBLIC_..., עם ה-caveat של rebuild (ראו למטה):
{inRollout("new-onboarding-flow", persona?.id) && <NewOnboardingBanner />}
```

`stableBucket(userId, feature)` מחזיר סלוט יציב 0-99 לכל זוג (משתמש,
פיצ'ר) — אותו משתמש תמיד נופל באותו סלוט לאותו פיצ'ר, כך שהוא **לא
"מהבהב"** בין הגרסה הישנה לחדשה בין רענון-עמוד, טאבים, או SSR מול קליינט.
כשמעלים את האחוז (10 → 50 → 100), כל מי שכבר "בפנים" נשאר בפנים.

## חוזה שמות משתני ה-env

שם הפיצ'ר → שם משתנה: אותיות גדולות, כל רצף תווים שאינו אות/ספרה (כולל `-`)
הופך ל-`_`. לדוגמה: `"new-pricing-engine"` →

| משתנה | שימוש | דורש deploy מחדש כדי שישתנה? |
|---|---|---|
| `ROLLOUT_NEW_PRICING_ENGINE_PCT` | שרת בלבד (API routes, server components/actions) | **לא** — Vercel קורא env vars server-side בזמן ריצה |
| `NEXT_PUBLIC_ROLLOUT_NEW_PRICING_ENGINE_PCT` | UI בצד לקוח | **כן** — Next.js משבץ (inline) משתני `NEXT_PUBLIC_*` בזמן ה-build, אז שינוי בערך דורש redeploy לפני שהוא נכנס לתוקף |

**חשוב להיות כנים על זה:** ה"בלי deploy" נכון רק למשתני השרת. לא להבטיח את
זה על משתני `NEXT_PUBLIC_*`.

ערך חסר/לא תקין (לא מספר, שלילי, מעל 100) → **100 (פתוח לגמרי)**. הסיבה:
flags נועדו להכיל דברים חדשים ומסוכנים בזמן ה-rollout — היעדר flag לא אמור
לכבות פיצ'ר בטעות. משתמש אנונימי (`userId` ריק/`null`/`undefined`) נכנס רק
כש-`pct === 100` — כלומר אנונימיים תמיד הקבוצה **האחרונה** לראות canary
(אין להם זהות יציבה שאפשר "להוציא" מהם בבקשה הבאה אם משהו משתבש).

## פלייבוק — rollout ו-rollback

1. שולחים את הפיצ'ר עטוף ב-`inRollout("my-feature", userId)`, בלי env
   מוגדר (⇒ 100%). שום דבר לא משתנה בפועל עדיין.
2. כדי להתחיל canary אמיתי: קובעים ב-Vercel (Production)
   `ROLLOUT_MY_FEATURE_PCT=10`. שרת → מיידי. לקוח (`NEXT_PUBLIC_`) →
   redeploy.
3. עוקבים אחרי לוגים/alerts/שיעור שגיאות בקבוצת ה-canary.
4. מרחיבים בהדרגה: 10 → 50 → 100, עריכת אותו משתנה — בלי שינוי קוד ובלי
   deploy חדש (בגרסת השרת).
5. Rollback: מורידים את הערך (או ל-0) באותו אופן — מיידי בגרסת השרת. זה כל
   סיפור ה-rollback על Hobby: אין תשתית-canary לבטל, רק את האחוז הזה.
6. כשפיצ'ר יציב ב-100% ונשאר שם — מסירים את ה-`inRollout(...)` מהקוד
   לגמרי. flags הם פיגום זמני, לא שטח קונפיגורציה קבוע.

## משימת המשך — לא מיושמת הלילה

**כלל:** ברגע שיש פיצ'ר כלשהו מתחת ל-100% (כל `ROLLOUT_*_PCT` /
`NEXT_PUBLIC_ROLLOUT_*_PCT` מוגדר לערך תקין מתחת ל-100), המצב הזה **חייב**
להופיע ב-daily digest (`src/app/api/cron/daily-digest` וכל מה שמזין אותו) —
כדי שלא נשכח canary "תקוע" באמצע rollout. זה **לא ממומש הערב**; זה סעיף
follow-up לסבב הבא (המימוש כנראה: לסרוק את שמות ה-env הרלוונטיים בזמן ריצה
של הדיגסט ולדווח את אלה שאינם 100/ריקים).
